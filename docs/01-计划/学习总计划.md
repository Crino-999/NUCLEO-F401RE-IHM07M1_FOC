## 一、任务定位

### 1.1 最终目标与评判标准

任务的价值排序：**收获知识 > 文档完善 > 代码可理解 > 项目跑通**。项目能转只是底线，不是目标；每一步学习都要留下可检索、可复盘的文档沉淀。

### 1.2 学习主线

电机控制（FOC 方向），承载平台为 NUCLEO-F401RE + X-NUCLEO-IHM07M1 开发板（2804 型电机）。

### 1.3 阶段策略

采用两段式：

1. **冲刺期（2026-08 → 2026-09/10）**：系统完成 FOC 电机控制的理论学习与工程实践。
2. **深潜期（基础达成后）**：进阶学习观测器、参数辨识、伺服算法、EtherCAT 等。

### 1.4 时间与精力约束

| 时段 | 用途 | 任务性质 |
|---|---|---|
| 周末完整时间 | 重度思考任务：FOC 原理、工程精读、仿真、上板实验 | 重 |
| 工作日晚上（碎片） | 轻任务：概念积累、协议学习、笔记整理 | 轻 |

工作日晚上已疲惫，不安排需要深度思考的任务。

### 1.5 学习方式

- 补课按"问题驱动"：遇到不会的概念再查，从问题发散深入原理，不做前置大段复习。
- 每个学习里程碑要求**独立完成**，核心算法代码不借助 AI 代写；AI 的角色是讲解原理、审阅实现、排查调试。
- 每次学习后由 AI 协助梳理成结构化文档，本人审阅后归档。

## 八、git 仓库管理方案

### 8.1 仓库定位

新建独立仓库（与历史 `STM32F103` 仓库分离），承载本次电机控制学习主线，建议同名 `NUCLEO-F401RE`。

### 8.2 分支策略

- `main`：主线。MC Workbench 工程、docs 文档随主线提交，保持 main 干净可追踪
- 实验性分支：仅用于尝试性修改（如某个算法变体），验证后合回 main 或删除
- 学习过程的分支不宜过多，主线即文档与代码的最终形态

### 8.3 提交规范

沿用已有习惯，`类型：描述` 格式：

- `docs:` 文档变更
- `feat:` 新功能/新实验
- `fix:` 修复
- `refactor:` 重构
- `chore:` 构建、配置等杂项

示例：`docs: 新增 FOC 坐标变换学习笔记`、`feat: 实现速度闭环核心代码`

### 8.4 提交节奏

- 每次学习/实验结束归档后提交一次，周末至少一次提交
- 文档与对应代码变更同次提交，保持可追溯
- 周复盘时核对本周提交，确认进度与日志一致

### 8.5 落地步骤

1. 本地：清理工作区（确认 `.gitignore` 覆盖编译产物、日志/备份文件），完成首次提交
2. 远程：GitHub 新建 `NUCLEO-F401RE-IHM07M1_FOC` 仓库（公开）
3. 关联：`git remote add origin` 并推送 main
4. 后续：按提交规范持续维护，每次 commit 前执行 8.6 隐私审查（L1+L2），push 前执行全量复核

### 8.6 提交前隐私审查与推送检查（固定机制，每次 commit / push 必须执行）

**背景**：2026-08-06 曾因历史版本中残留敏感文字（岗位要求原文、个人背景摘要）导致公开仓库泄露。本仓库定位为 GitHub 公开仓库，任何 commit 的内容都可能被陌生人长期查看，因此隐私审查的时机必须**前置到 commit 之前**，且不能只做关键词扫描——关键词命中只是底线，**实际描述的内容是否适合公开**才是审查重点。

**两阶段时机**：

- **commit 前（强制）**：对本次 staged 变更执行 L1 关键词/文件扫描 + L2 内容语义审查，用户终审通过后才允许 commit
- **push 前（强制）**：对 HEAD 全量历史执行 L1 全量扫描，推送完成后远程克隆复核

**敏感词表**：本地文件 `.git_sensitive_words.txt`（仓库根目录，已在 `.gitignore` 中排除，禁止提交）。该文件包含个人敏感词，审查时以它为词表执行扫描。**注意：词表文件自身含敏感词，任何情况下不得 add 进 git**。

#### L1 关键词 / 文件扫描（本地命令）

commit 前（staged 变更）：

1. **文件名扫描**：`git diff --cached --name-only | Select-String -Pattern "($(Get-Content .git_sensitive_words.txt | Where-Object { $_ -and -not $_.StartsWith('#') } | ForEach-Object { [regex]::Escape($_) }) -join '|')"`
2. **变更内容扫描**：`git diff --cached -U0 | Select-String -Pattern "($(Get-Content .git_sensitive_words.txt | Where-Object { $_ -and -not $_.StartsWith('#') } | ForEach-Object { [regex]::Escape($_) }) -join '|')"`
3. **本机路径 / 用户名扫描**（动态取值，不写死）：`git diff --cached -U0 | Select-String -Pattern "($env:USERPROFILE.Replace('\','\\')|$env:USERNAME|$((git rev-parse --show-toplevel).Replace('\','\\')))"`
4. **提交身份**：`git config user.email` 必须为 GitHub 隐私邮箱（noreply 格式，见 8.7 节）

push 前（全量历史，沿用原清单）：

1. **工作区状态**：`git status` 确认无未提交改动，提交信息规范（`docs:`/`feat:`/`fix:` 前缀）
2. **历史文件名扫描**：`git log --all --name-only --pretty=format: | Select-String -Pattern "($(Get-Content .git_sensitive_words.txt | Where-Object { $_ -and -not $_.StartsWith('#') } | ForEach-Object { [regex]::Escape($_) }) -join '|')"`
3. **HEAD 内容扫描**：`git grep -l -E "($(Get-Content .git_sensitive_words.txt | Where-Object { $_ -and -not $_.StartsWith('#') }) -join '|')" HEAD -- .`
4. **本机路径 / 用户名扫描**：HEAD 全文件不得出现本机绝对路径前缀与 Windows 用户名
5. **提交作者**：`git log --format='%an <%ae>'` 确认全部使用 GitHub 隐私邮箱
6. **推送后复核**：推送完成后从远程重新克隆，对克隆副本重复执行第 2、3 项扫描，确认远程与本地一致

#### L2 内容语义审查（新增，重点）

原则：以「一个陌生人读到这段描述」为视角，判断内容本身是否适合公开，而非仅看是否命中关键词。

**不可提交的典型内容**（随项目演进可扩充，扩充项登记到决策记录）：

- 个人身份：真实姓名、非公开邮箱、电话、地址、Windows 用户名、本机绝对路径、其他个人账号
- 个人经历：现任/曾任雇主、公司内部项目与代码细节、未公开仓库名称与内容、同事/客户信息
- 职业隐私：职业规划、目标公司与岗位要求原文、收入与期望收入等内部细节
- 过程性内容：与 AI 的对话记录、未审阅草稿、可反推出真实身份的个人反思/失败细节
- 凭据：token、密钥、证书、内网地址

**三个自检问题**（任一为「是」即不可提交）：

1. 陌生人能据此推断出我的真实身份、雇主或位置吗？
2. 招聘方看到这段内容，会看到我不想公开的职业信息吗？
3. 这段描述放进公开仓库，现在和将来都不会尴尬吗？

**执行方式（L2 默认由主代理执行；本地 Worker 仅做初筛）**：

- L2 属于判断/审核类工作，由主代理按本清单逐项审查 staged 变更，输出「可提交 / 待确认 / 不可提交 + 文件:行号 + 理由」，交用户终审
- 本地 Ollama MCP Worker（vision / doc-worker）仅做机械初筛（截图文字识别、文档要点提取）；敏感内容一律传文件路径，不粘贴正文；不可用时跳过
- 如需独立复核，可另派 Codex 子代理（`spawn_agent`，`fork_turns="none"`，只传文件路径清单）；**Codex 子代理走云端模型，不是本地 Worker**
- 用户终审是唯一放行依据；AI 生成的文档/代码与手写内容同等对待，一律过审

**通过标准**：L1 零命中；L2 无可提交障碍项；用户明确确认。任一不通过即禁止 commit / push。

**扩展规则**：任何涉及"公开仓库内容检查"的场景（新建笔记、实验记录归档、AI 生成文档）都按此清单执行；敏感词可随时追加到 `.git_sensitive_words.txt`。

### 8.7 提交身份

本仓库提交必须使用 GitHub 隐私邮箱（noreply 格式，防止真实邮箱随提交泄露）。当前全局 git 邮箱若为真实邮箱，已在仓库级配置覆盖。检查方式：`git config user.email`。

## 九、AI 协作原则

| 场景 | AI 的角色 |
|---|---|
| 原理讲解 | 用通俗语言讲清概念，配合推导与图示 |
| 笔记梳理 | 每次学习后协助生成结构化文档，供审阅 |
| 代码审阅 | 审查本人实现，指出问题并解释原因 |
| 调试排错 | 协助定位问题方向，不直接代写核心算法 |
| 提交前隐私审查 | 每次 `git commit` 前执行 8.6 检查（L1 扫描 + L2 内容语义审查，本地子代理优先，用户终审）；`git push` 前执行全量复核 |
| 禁止事项 | 不代写 FOC 核心算法代码；不虚构学习进度或实验数据 |
